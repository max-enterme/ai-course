もくじ ことば集

第4章

輪を回して、作りたいものを1機能ずつ作る

Lv1〜3 言葉にする → 証拠で確かめる目安 周を重ねる(約29時間)

作りたいものそのものを、1周に1機能ずつ作っていきます。作る前に相談役の ChatGPT と「何を作るか」を言葉にし、作ったら確かめて、振り返って次の周へつなぎます。周を重ねながら、Lv1 → Lv2 → Lv3 と上がっていきます。

この章のゴール

  • 相談役の質問に答えて、intent.md・spec.md・plan.md を決めてから作れる
  • 相談役が出した PR のブランチで作ってもらい、確かめてマージできる
  • 壊れたとき、材料をそろえて AI に調べさせ、直ったかを自分で確かめられる
  • テストと AI レビューで確かめてから、マージできる

この章の進み方

この章は長い章です。1回の授業でおよそ1周を回し、周を重ねて段階を上げます。周の形はずっと同じで、段階が上がるごとに「確かめ方」が増えます。

エラーが起きたとき・条件をうまく言えないとき・手で確かめるのが大変になったときは、その周の中で講師と一緒に扱います(下の「その場で扱うこと」)。

2つの AI の役割

相談役作る役
道具ChatGPT(リモート)Antigravity(ローカル)
すること質問して「何を作るか」を一緒に決める。下書きと PR を作る。PR のレビューもする今のコードに合わせて作る順番を直し、作って、動かして確かめる
手が届く場所GitHub の上自分の PC のフォルダ

決めるのは あなた です。相談役は「おすすめの答え」を付けてくれますが、そのまま全部通さず、自分の言いたいことかを見て答えます。

準備(最初に1回だけ)

  1. ChatGPT と GitHub をつなぐ。private のリポジトリは、GitHub 側で ChatGPT に All repositories へのアクセスを許可しないと読めません
  2. 講師と一緒に README.md を読み直し、作りたいものが今の考えと合っているかを確かめる。変わっていれば Antigravity に直してもらって push する
  3. ChatGPT にプロジェクトを作り、記憶を「プロジェクト内だけ」にする。プロジェクトの「指示」に、下の文面を入れる(<...> のところは講師と README.md から埋めます)
相談役に入れる「指示」の文面(コピーして使う)
# このプロジェクトについて
<作りたいものを1〜2文。使う人の目線で、作り方は書かない>
リポジトリは GitHub の <owner/リポジトリ名>。話す前に必ず今のリポジトリ(README.md・AGENTS.md・specs/・今のコード)を読む。作りたいもの(最終像)は README.md を正とする。リポジトリを見れば分かることは私に聞かない。読めなかったときは、そう言う。
使う人(私)はプログラミングを勉強中。説明は短い日本語で、専門用語にはその場で一言説明を付ける。

# あなたの役割
「何を作るか」を一緒に決める相談役。作るのは別の AI なので、コードは書かない。作る順番(plan.md)は下書きまで書き、今のコードに合うかは作る AI が確かめる。
- 決めるのは私。私が答えていないことを決めて書かない。機能を足す提案はしてよいが、私が「入れる」と言うまで入れない
- 1周で決めるのは1つの機能だけ
- ルール(点数・料金など)は、私が言ったものだけを使う

# 「次の周を詰めて」と言われたとき
質問は1回に3つまで。番号を付け、それぞれに「おすすめの答え」を1つ添える。おすすめは一番小さく作れる案にする。前の答えで変わる質問は、答えを聞いてから聞く。次の順に聞く。
1. 前の周があれば、その結果: できたこと / AI がうまくいかなかったこと(どう気づいたか)。うまくいかなかったことは、次から防ぐ1行の案にする(AGENTS.md があれば足す。無ければ、作る AI への頼み方に足す1行として見せる)。足すかは私が決める
2. やりたいこと(1つだけ。README.md に「ステップ目標」や「完成の条件」があれば、今の段のまだ満たしていないものから選ぶ)
3. なぜ(誰が・どんな場面で・何が嬉しいか)
4. やらないこと(難しい自動化は、まず手で入力する形にして外す)
5. 完成の条件: 3つまで。私が画面を触って確かめられる文にする。数(何人分・何回・いくつまで)と、空のまま・間違えて入れたときの動きは必ず聞く
6. 外部のサービス・パスワードや API キー・お金・他の人が作った画像やロゴ・個人情報に当たるなら、止めて「講師に相談してください」と言う
聞くことが残っていなければ、intent.md(やりたいこと・なぜ・やらないこと)と spec.md(完成の条件)の下書きを見せる。
OK が出たら、plan.md(作る順番)の下書きを見せる。書き方:
- 1ステップ = 作って画面で確かめられる1かたまり。一度に全部作る順番にしない
- 各ステップに、確かめる spec.md の条件と、確かめ方(何を押して・何が出ればよいか)を書く
- 今のリポジトリのファイルと書き方に合わせる。新しいファイル・道具を足すなら理由を書き、私に聞く
- spec.md に無い機能を足さない。spec.md に無いが決めないと作れないこと(例: 同じ値を2回入れたら)は、下書きを見せる前に私に聞く。答えは spec.md にも足す
- 各ステップに、変える場所を書く: ファイル名と、その中の場所(関数の名前・画面の部分など、コードの中で探せる名前)。行番号は目安として添えてよい(実装が進むとずれるので、名前の方を正にする)。新しく作る場所は「新しく作る」と書く
- plan.md の最初に「読んだファイル」を並べる。読めなかったファイルがあれば、そう書く
- コードそのものは書かない(場所と、何をするかの説明まで)
私が「OK」と言うまで PR は作らない。
OK が出たら specs/<3桁の番号>-<英小文字とハイフンの名前>/ に intent.md・spec.md・plan.md を置き、同じ <番号>-<名前> のブランチで PR を作る。番号は specs/ の続き(無ければ 001)。PR の本文には、spec.md の条件を「- [ ]」のチェック欄にして並べる。この PR は、この後の実装も積むので、私に「マージして」と言わない。決まった「次から防ぐ1行」は、AGENTS.md があれば足して同じ PR に入れ、無ければ PR の本文に書く。前の周のファイルは変えない。

# PR のレビューを頼まれたとき
次の観点で見て、「重大」と「軽微」に分けて答える。軽微は5個まで。
- バグ: 動かない・壊れる
- 危険: パスワード・API キー・個人情報が入っている、外部にデータを送っている
- ずれ: spec.md・plan.md と違う、spec.md に無いものを作っている
「重大」= 動かない・情報が漏れる・spec.md の条件を満たさない。見た目や名前の好みは「軽微」。

# 書かないこと
- 実在の人の名前・連絡先(見本は「A」「B」などの仮の名前にする)
- パスワード・API キー

3つのファイル

1周ごとに specs/001-<名前>/ のようなフォルダができて、その中に置かれます。自分で書き起こす必要はありません。 相談役が質問し、あなたが答えると、下書きが出てきます。

ファイル中身
intent.mdやりたいこと / なぜ(誰が・何が嬉しい)/ やらないこと
spec.md完成の条件。自分で触って確かめられる文
plan.md作る順番。相談役が下書きし、作る役が今のコードと照らして直す

spec.md の例:

- [ ] タスクを入力して「追加」を押すと、一覧の一番下に出る
- [ ] 空欄のまま「追加」を押しても、一覧は増えない
- [ ] 10件まで追加できる

1周の流れ(毎周同じ)

1周は 1つのブランチと1つの PR で通します。マージは最後に1回だけです。

相談役と決める → PR(intent・spec・plan の下書き)を読む【まだマージしない】
→ そのブランチに切り替える → 作る役が plan.md を見直す【納得してから】
→ 同じブランチで作って push →(Lv3: テスト・AI レビュー)→ 条件を確かめてマージ → main に戻して pull
  1. 相談役のプロジェクトで 新しい会話 を開き、1行送る(最初の周は、作りたいものの一番小さい版)
次の周を詰めてください。今やりたいこと: 〜
  1. 質問に答える。おすすめでよければ「1はおすすめで」、違えば自分の言葉で答える
  2. intent.md・spec.md の下書きを読み、よければ「OK」と送る。続けて出る plan.md の下書きも、1つ作るごとに確かめられる順番かを見て「OK」と送る
  3. 相談役が作った PR を読む。まだマージしません。見るところ:
    • 自分の言いたいことになっているか
    • やらないことが書いてあるか
    • 完成の条件を、自分で触って確かめられるか
    • 数(何件・何人・何回)が書いてあるか
    • plan.md が、一度に全部作る順番になっていないか
  4. 手元でその PR のブランチに切り替える。Antigravity に頼む場合(モデルは Gemini Flash で大丈夫です):
GitHub のブランチ <番号>-<名前> に切り替えてください。
  1. Antigravity の新しい会話で、plan.md を今のコードと照らして直してもらう
specs/<番号>-<名前>/ の spec.md と plan.md を読み、今のコードと照らして plan.md を見直してください。
特に、各ステップに書いてある「変える場所」が今のコードに本当にあるか、そこを変えれば足りるか(他にも変える場所がないか)を見てください。
合わないところ・このままだと作れないところだけ直し、何をなぜ直したかを教えてください。直すところが無ければ、そう言ってください。
spec.md に無いことで決める必要があるものが見つかったら、決めずに質問として plan.md の最後に書いてください。まだコードは変えないでください。直したら plan.md を commit してください。
  1. 直した理由に納得したら、同じ会話で作ってもらう(新しいブランチや PR は作らせません)
今のブランチのまま plan.md の順に実装してください。ステップごとに確かめて commit し、終わったら push してください。新しいブランチと PR は作らないでください。
spec.md の条件ごとに「どう確かめたか・結果」を報告してください。
  1. spec.md の条件を1つずつ確かめ、PR の本文のチェック欄に印を付ける(Lv3 からは、その前にテストと AI レビュー)
  2. マージして、手元を main に戻して pull する(GitHub でマージしても、手元のファイルは pull するまで変わりません)
  3. 次の周の会話で、最初に聞かれる振り返りに答える

振り返り(ファイルにはしません)

できたこと
AI がうまくいかなかったこと   ← どうやって気づいたか / 次の頼み方か AGENTS.md に何を足すか
次にやりたいこと             ← これが次の周の intent.md になる

ステップ目標(完成までの段)

最初の1〜2周が回ったら、講師と一緒に、作りたいものの完成までを 3〜5つの段 に分けます。周を重ねるだけだと、次に何を作るかが毎回その場の思いつきになりがちだからです。

  • 1つの段は「そこで止めても使える」形にします
  • 段ごとに「できたら次へ」の条件を1〜3つ付けます(spec.md と同じく、自分で確かめられる文)
  • 手で入れる形を先に仕上げます。あとで自動にしても、後ろの処理は同じものを使います
  • 難しい自動化(画像を読む・外部のサービスとつなぐ など)は1つの段にして、その段の最初の周は「どうやるか」を試して決めるだけにします
  • 段は README.md に「ステップ目標」として書いてもらい、push します。相談役は、今の段のまだできていないものから次の周を選びます。段は途中で変えて大丈夫です

段階を上げる目安

段階周の中で足すこと上がる目安
Lv1 言葉にする相談役と決めてから作る。条件は自分で確かめてマージ入力・処理・出力を説明できる / 1周を最後まで回せた / 下書きのどこが自分の言いたいことと違ったかを言えた
Lv2 決めてから作る完成の条件に「ふだんと違う入れ方」も入れる。plan.md に納得するまで作らせない。条件を全部、手で確かめる条件付きの変更を AI に伝わる形で頼めた / 壊れたときに材料を渡して調べさせ、直ったかを確かめた / 条件を全部、自分の手で確かめた
Lv3 証拠で確かめるテストを作らせて走らせる。PR を AI にレビューさせ、指摘に対応してからマージ。AGENTS.md に足した約束が効いたかを確かめ、長くなったら削るテストの結果で完成を判断できた / AI レビューから指摘への対応・マージまで一人で回せた / AGENTS.md に足した約束が効いたかを言え、1回以上削った

進む速さは人によって違って大丈夫です。1つの段階に何周かけてもかまいません。

その場で扱うこと

次のことが起きたら、その周の中で扱います。講師が一緒に進めるので、ここは「そのとき開いて見る」場所です。

条件をうまく言えないとき — 指示に使う言葉

書けるようになる必要はありません。AI に頼むときに使う言葉です。

ことば一言で頼むときの言い方
変数データに名前を付ける「この値は後で使うので覚えておいて」
条件分岐「もし○○なら」「空のときは追加しないで」
配列複数のデータをまとめる「一覧として持っておいて」
繰り返し一覧を1つずつ処理する「全部について同じことをして」
関数処理に名前を付ける「この手順を1つにまとめて、名前を付けて」

自分のアプリが何を覚えているかは、AI に説明してもらえます。

このアプリは何をどこに覚えていますか。画面の動きと並べて、初心者向けに説明してください。

閉じて開き直し、データが残るか消えるかも自分で確かめます。

壊れたとき — 不具合の伝え方

原因を調べるのは AI の仕事です。あなたの仕事は、材料を渡すことと、直ったかを確かめることです。

① 何をしたか(同じ順でもう一度できる書き方で)
② 実際に何が起きたか
③ 本来どうなってほしかったか
④ エラー表示があれば、そのまま貼る(意味は分からなくてよい)

調べることと、直すことは別。AI にも、先に調べさせる。

追加ボタンを押しても一覧に出ません。本来は入力した内容が一覧に出るはずです。
まず原因を調べてください。修正はまだしないでください。

調べた結果を聞いてから直してもらい、最初と同じ手順でもう一度やって、直ったか・他のところが壊れていないかを見ます。同じエラーが2回続いたら、モデルを Claude Sonnet に替えて同じことを頼みます。

完成の条件を決めるとき — 境界のケース

ふだんと違う入れ方をしたときにどうなるかも、完成の条件です。

  • 空欄のまま / 0 や マイナス / とても大きい数 / とても長い文字 / ボタンの連打
  • 画面のないものなら: 空のファイル / 形が違うデータ

相談役は「空のまま・間違えて入れたとき」と「数」は毎回聞いてくれます。それ以外は聞かれないことがあるので、下書きを読むときに自分で探し、要るものは「〜のときの条件も足して」と頼みます。

手で確かめるのが大変になったとき — テスト

spec.md の条件から、自動で確かめる仕組み(テスト)を作ってもらいます。道具は講師と決めます(Web なら Playwright Test)。

spec.md の条件を1つずつ確かめるテストを Playwright で作ってください。
条件1つにテスト1つ以上。テストの名前は spec.md の条件の文をそのまま使ってください。

テストを実行してもらい、結果を読みます。わざと1か所壊して、テストが失敗するのも見ます。一度入れたら、次の周からも毎周テストを足します。

任せても、確かめる。テストが通っても、自分での確認はやめない。

同じ失敗が続くとき — AGENTS.md を育てる

振り返りで出た「AI がうまくいかなかったこと」は、AGENTS.md(AI への約束)に1行足して防ぎます。足すだけだと長くなって守られにくくなるので、確かめる・削るまでをセットにします。

  • 足すきっかけ: 同じ失敗が続く / 毎回同じことを頼み方に書いている / AI レビューで同じ指摘が2回出た
  • 足すのは、その周のブランチで Antigravity に頼みます
  • 足したら、新しい会話で約束を言わせて、読まれているか確かめます(第2章と同じ確かめ方)
  • 次の周で、同じことが起きなくなったかを見ます
  • 長くなったら削ります。当たり前に守られていること・一度しか起きなかったことは消して大丈夫です。目安は1画面に収まる長さです

足す約束の例:

- 実装の前に既存のコードを調べる
- plan.md に納得してもらうまでコードを変更しない
- 実装後は動作を確かめ、テストを実行する
- エラーを隠さない

AI レビューで同じ指摘が2回出たら、AGENTS.md に足す。

マージする前に — AI レビュー(Lv3 から)

コードを書いた AI(Antigravity)自身には、レビューさせません。

誰が何を見るかコードを読むか
AI レビューバグ・危ないところ・spec.md / plan.md とのずれ読む
あなた実際に触って、spec.md の条件を満たすか読まない
講師「講師を呼ぶとき」に当たるところだけ原則読まない

相談役の ChatGPT で、intent・spec を決めた会話とは 別の新しい会話 を開いて頼みます。

<PR の URL> をレビューしてください。

結果が出たら「PR にコメントとして投稿してください」と頼みます。「重大」の指摘は作る役に直してもらいます。直さないと決めたときは講師を呼びます。

マージしてよい条件: テストが通っている / 「重大」の指摘が残っていない / 自分で条件を全部確かめた / 「講師を呼ぶとき」に当たらない

講師を呼ぶとき

  • パスワード・API キー・ログインの仕組みを扱う
  • 個人情報を扱う、または公開する
  • お金がかかるサービスにつなぐ
  • 外にデータを送ったり、外から受け取ったりする機能を足す
  • 他の人が作った画像・絵・ロゴを使う
  • AI レビューの指摘を「直さない」と決めた
  • 段階(Lv)が上がるとき

どのモデルを使うか

基本は Gemini。「確認」と「2回やってダメだったとき」だけ Claude に替える。

授業の初めと終わりに、Gemini 側と Claude 側の残りの使用量を控えておきます。
